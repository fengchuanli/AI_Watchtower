AI Watchtower RAG 设计图

从你的 Mac 到 Azure 的整体结构。黄色是「把资料放进搜索库」的流程，蓝色是「提问 → 得到带引用的回答」的流程。图上的字母和数字，对应下面的步骤说明。

整体结构

① 建索引：把资料放进搜索库

什么时候跑：第一次搭建时、Codex 更新了新闻之后。不跑的话，新新闻搜不到。

  1. →
    读资料并切分。规则文档和新闻合成 265 篇，切成 1273 个约 800 字的 chunk。rag/scripts/ingest_docs.py → chunk_docs.py
  2. A
    生成向量。把每个 chunk 发给 text-embedding-3-small，拿回 1536 个数字，存进缓存。已经生成过的不再调用，所以每天只处理新增的部分。build_embedding_cache.py
  3. B
    上传到 Azure AI Search。chunk 正文、出处（source / title）和向量一起上传，检索结果才能标出处。prepare_vectorized_azure_search_docs.py → azure_search_index.py upload

② 提问：得到带引用的回答

每次提问大约 1〜2 秒，费用约 0.3 日元。

  1. 1
    问题变向量。用同一个 embedding 模型把问题也变成 1536 个数字。必须用同一个模型，否则无法比较。
  2. 2
    向量检索。在 AI Search 里找和问题意思最接近的前 5 个 chunk。不做来源筛选，纯向量检索（25 题评测里效果最好）。
  3. 3
    交给 gpt-5.4-mini。把 5 段资料编号 [1]〜[5]，规定「只能用这些资料、每句标引用、没有依据就说资料不足」。
  4. 4
    检查后返回。程序删掉模型编造的引用编号，再把回答和出处显示出来。ask_pipeline.py --retriever azure-vector --generator azure

在 AI Watchtower 网站上加一个提问框。API key 不能放在浏览器里，所以中间要加一层 API，把 key 保管在 Azure 上。

浏览器（提问框） → Azure Functions（API，保管 key） → ② 的流程（向量检索 + gpt-5.4-mini） → 回答 + 引用

做过的设计决定

  • 检索用纯向量，不用 hybrid。25 题评测里纯向量 MRR 0.87，hybrid 0.78。新闻里的固定字段（「来源:」「可信层级:」）干扰了关键词检索。
  • 不做来源类型的自动筛选。规则会把「已经发布的新闻数据出错了」这类问题误判成新闻题，正确文档被筛掉（100% → 84%）。
  • 「资料不足」交给模型判断。只看相似度分数时，有答案和没答案的题分数重叠；改由 gpt-5.4-mini 判断后，5 题全对。
  • 向量 int8 压缩、不保存副本。Free 层 50 MB 快满了，压缩后 47.6 → 17.0 MB，检索结果不变。
  • 安全。key 只放在 .env，不进 Git；Azure OpenAI 只允许你家的 IP 访问；模型只能引用真实存在的资料编号。
